## 2. Summary

`SelfNodeRemediationConfig.spec.minPeersForRemediation` is rendered onto the agent
DaemonSet as `MIN_PEERS_FOR_REMEDIATION`, but before the RHWA-1872 fix the agent never read
that variable and used the Go zero value `0` instead. This test configures a minimum the
node under test can never satisfy, cuts the agent off from the api-server, and asserts the
agent refuses to consult peers *because of the configured minimum* — which only happens when
the value actually reached the agent's `ApiConnectivityCheckConfig`.

## 3. Scope

- **In scope**: the agent's effective `MinPeersForRemediation`. That the controller renders
  `MIN_PEERS_FOR_REMEDIATION` from the SNRC onto the running agent pod, and that the agent,
  on losing api-server access with fewer worker peers than the configured minimum, takes the
  "insufficient number of peers" branch of `getWorkerPeersResponse`, names the configured
  minimum in its log, treats itself as healthy, and does not reboot the node.
- **Out of scope**:
  - The remediation path itself — that an unhealthy node with a `SelfNodeRemediation` CR
    reboots, and that remediation strategies evict workloads. Covered by
    `worker_remediation.go` and `master_remediation.go`.
  - The `minPeersForRemediation: 0` isolated-node behaviour (`UnHealthyBecauseNodeIsIsolated`
    leading to a reboot when a node has no peers at all). Reaching it needs a single-worker
    cluster, and a pre-fix build would reboot the node there rather than fail an assertion;
    this spec deliberately requires ≥ 2 workers so it fails by assertion on a pre-fix build.
  - Control plane agents. The spec patches the one cluster-wide SNRC, so every agent picks
    the value up, but it injects the fault on and asserts against a worker only; control
    plane peer handling is `master_remediation.go`.
  - The remaining `ApiConnectivityCheckConfig` fields PR #363 also routed through
    `getApiConnectivityCheckConfigFromEnv` (`API_CHECK_INTERVAL`, `HOST_PORT`, …). Those were
    already read before the fix; `config_lifecycle.go` and `upgrade_lifecycle.go` cover
    SNRC-to-DaemonSet propagation generally.
  - The other SNRC field defaults and their CRD validation, covered by `crd_negative.go`.

## 5. Preconditions

1. The SNR operator is installed in `openshift-workload-availability` and
   `self-node-remediation-controller-manager` is Ready. `BeforeAll` pulls the deployment and
   asserts `IsReady` within `medik8sparams.DefaultTimeout`.
2. The cluster has at least `snrparams.MinWorkersForPeerCheck` (2) Ready worker nodes.
   `BeforeAll` counts them with `helpers.CountReadyWorkerNodes` and `Skip`s with the observed
   count when there are fewer, because a node with no peer at all exercises the
   out-of-scope isolated-node path instead.
3. A worker node is selectable as the node under test. `BeforeAll` uses
   `helpers.SelectWorkerNode`, which avoids the SSH bastion node.
4. Every SNR agent DaemonSet pod is Running with ready containers, so the peer list the
   agent builds is complete before the value is changed. `BeforeAll` waits for
   `verifyDSPodsRunning` within `snrparams.DSPodRestartTimeout`.
5. No stale state needs deleting: the spec creates no CR. It patches the single default
   `SelfNodeRemediationConfig`, reads the pre-existing `minPeersForRemediation` first, and
   restores it in `DeferCleanup`.

## 6. Test steps

| #  | Step (`By` text) | Expected result |
| -- | ---------------- | --------------- |
| 1  | `Verifying the SNR controller-manager deployment is ready` | `self-node-remediation-controller-manager` is Ready within `medik8sparams.DefaultTimeout` |
| 2  | `Verifying the cluster has at least 2 Ready worker nodes` | `helpers.CountReadyWorkerNodes` returns ≥ 2; otherwise the spec skips, naming the count it found |
| 3  | `Selecting the worker node under test` | A Ready, non-bastion worker is chosen |
| 4  | `Verifying the SNR agent DaemonSet pods are Running` | Every agent pod is Running with ready containers within `snrparams.DSPodRestartTimeout` |

| 6  | `Patching the SelfNodeRemediationConfig with minPeersForRemediation above the available peer count` | The merge patch setting `minPeersForRemediation` to the value under test is accepted |
| 7  | `Waiting for the SNR agent DaemonSet pods to be replaced and Ready` | No pre-patch pod UID survives and every agent pod is Running and ready within `snrparams.DSPodRestartTimeout` |
| 8  | `Letting every agent re-discover its peers after the rollout` | Every agent pod stays Running and ready for `snrparams.PeerListSettleTimeout` (1 minute, four peer-update intervals) |
| 9  | `Asserting the agent container on the node under test carries MIN_PEERS_FOR_REMEDIATION` | The `manager` container of the agent pod on the node under test has `MIN_PEERS_FOR_REMEDIATION` equal to the value under test |
| 10 | `Resolving the kubernetes API server cluster IPs` | Service `default/kubernetes` reports at least one cluster IP |
| 11 | `Recording the boot ID of the node under test` | `status.nodeInfo.bootID` is read and non-empty |
| 12 | `Blackholing the API server addresses inside the agent pod, restoring them automatically` | A single blocking exec adds a blackhole route per api-server IP in the agent pod's network namespace, sleeps `snrparams.APIDisconnectDuration`, then deletes each route; exec errors are logged, not fatal |
| 13 | `Asserting the agent reported an insufficient number of peers with the configured minimum` | The agent log contains `insufficient number of peers found` together with `"minPeersRequired": <value under test>` within `medik8sparams.DefaultTimeout` |
| 14 | `Asserting the node under test did not reboot and is still Ready` | The boot ID is unchanged and the node's `Ready` condition is still `True` |

Steps 1–4 run in `BeforeAll`; steps 5–15 are the `It`.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1972")` runs and passes.
- The `manager` container of the agent pod on the node under test carries
  `MIN_PEERS_FOR_REMEDIATION` equal to the patched `minPeersForRemediation`, which is at
  least the Ready worker count and therefore always ≥ 2, always one more than the most peers
  a single worker can see, and always different from the CRD default of 1.
- While the agent cannot reach the api-server, its log contains
  `insufficient number of peers found` *and* a `"minPeersRequired"` field whose value is that
  same number. This is the assertion the bug fails: an agent that never reads
  `MIN_PEERS_FOR_REMEDIATION` uses `0`, `len(peersToAsk) < 0` is never true, so it asks its
  peers and the message is never logged.
- The node under test does not reboot — `status.nodeInfo.bootID` is byte-identical before and
  after the fault — and its `Ready` condition is still `True`.
- Cleanup finishes: no blackhole route remains in the agent pod,
  `minPeersForRemediation` is back to the value read in step 5, and every agent pod is
  Running and ready again within `snrparams.DSPodRestartTimeout`.

## 8. Failure / known issues

None.

The spec is not gated. RHWA-1872 is fixed in SNR 5.8.0 by self-node-remediation PR #363, so
the spec passes on any build from that PR onwards.

On a pre-fix build it fails at step 13: the agent reaches the peer-check path and logs
`Aggregate peer health responses` instead, because its effective `MinPeersForRemediation` is
`0`. That is the intended regression signal, not a known issue. Requiring ≥ 2 workers keeps
that failure an assertion failure: with a real peer to ask, a pre-fix agent is told it is
healthy and the node still does not reboot.

## 9. Cleanup

- `DeferCleanup` (registered last, just before the fault, so it runs first) removes any blackhole route
  left in the agent pod. It tolerates a vanished pod, logs failures with
  `GinkgoWriter.Printf` instead of failing, and — if a route somehow survives — deletes the
  agent pod so the DaemonSet recreates it with a clean network namespace. In the normal path
  there is nothing to do: the injecting command deletes the routes itself.
- `DeferCleanup` (registered first, so it runs last) restores
  `spec.minPeersForRemediation` to the value read in step 5, removing the field when it
  was unset so the CRD default of 1 applies, then waits for every agent pod to be Running and
  ready again.
- `AfterAll` removes nothing: `BeforeAll` creates no resource.
- Recovery runs even when the spec failed mid-way, because both cleanups are `DeferCleanup`
  closures registered before the step that can fail. No node recovery is needed — the spec
  never cordons a node, stops a kubelet or changes a host route.

## 12. Implementation sketch

Implemented in
[`tests/snr-operator/tests/min_peers_for_remediation.go`](../../tests/snr-operator/tests/min_peers_for_remediation.go).

The fault is injected from inside the agent pod's own network namespace — the agent container
is privileged and ships `iproute` for exactly this purpose — so the node, its kubelet and
every other pod on it keep full api-server access:

```go
It("Verify the SNR agent uses the configured minPeersForRemediation value",
    reportxml.ID("1972"),
    Label(labels.TierResiliency, labels.PlatformAny,
        labels.ComponentRemediation), func() {
        // minPeersUnderTest is the Ready worker count: one more than any
        // peer count a single worker can observe.
        blackholeAPIForAgent(agentPodName, apiIPs)

        Eventually(func() error {
            return agentLoggedInsufficientPeers(agentPodName, minPeersUnderTest)
        }, medik8sparams.DefaultTimeout, snrparams.DefaultPollInterval).Should(Succeed(),
            "Agent pod %q must log %q with minPeersRequired=%d; a pre-RHWA-1872 agent "+
                "ignores MIN_PEERS_FOR_REMEDIATION and uses 0 instead",
            agentPodName, snrparams.MinPeersInsufficientMessage, minPeersUnderTest)
    })
```
